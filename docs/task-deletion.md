# Архив и остановка задач

Архивирование и подтверждение остановки — независимые состояния.
`POST /api/projects/:projectId/tasks/:taskId/archive` принимает `request_id`
и `state_version`. Ownership и версия проверяются до побочных эффектов.
Одна транзакция сохраняет `archived=1`, блокирует новые действия, отзывает
pending human requests и queued/sending chat. Сразу после этого контроллер
снимает scheduler jobs и начинает остановку. Ответ не ждёт окончания процессов.
Повтор запроса возвращает сохранённый ответ без повторного архивирования.

SQLite v14 добавляет `archived`. `snapshot.tasks` содержит доску,
`archived_tasks` — архив. SSE обновляет обе вкладки. Уже удалённые в v13
карточки доступны в архиве; прежние failed-удаления остаются на доске,
пока пользователь явно не архивирует их. История и файлы не удаляются.

Существующий `deletion_state` сохраняет результат остановки: `stopping`,
`failed` (не подтверждена), `deleted` (подтверждена). Имена полей и старый
`/delete` сохранены для совместимости. Новая кнопка использует `/archive`,
повтор остановки в архиве и на автоматически восстановленной карточке — `/stop`. Архивирование не очищает
`stop_unverified` или `execution_unverified`, не является ручной сверкой
и не освобождает слот незавершённого callback/известной process group.
Совместимый `/delete` также сохраняет ручной архив в транзакции принятия запроса,
даже если остановка ранее восстановленной карточки уже подтверждена. Синхронизация
не может заменить это решение автоматическим архивом во время остановки.
Поздние callbacks не возобновляют pipeline и не меняют видимость карточки, выбранную архивированием или синхронизацией.

Остановка посылает TERM известным POSIX process groups, затем KILL через
500 ms; до 5 s ждёт исчезновения известных групп и callbacks. `ps` не доказывает
отсутствие orphaned detached-потомков. Каждый зарегистрированный процесс
сохраняет `stop_unverified`; исчезновение известной группы его не снимает.
При неопределённости архив показывает предупреждение и данные для сверки.
Историческое исполнение баз до v13 также помечается неподтверждённым.
После restart процессам прежнего backend автоматически не отправляются сигналы.

`/stop` позволяет повторить остановку без текста подтверждения.
Необязательный `reconciliation` (20–4096 символов) означает фактическую
ручную проверку отсутствия процессов и remote результата. Она сохраняется
в `task.stop-verified-by-human`; backend не выдаёт её за собственное доказательство.
Проверка известных групп выполняется и после ручного подтверждения.

В архиве доступны описание и редакции, сообщения, runs, отчёты и redacted логи.
Read-only API проверяет project/task/run ownership; команды архивной карточки по-прежнему запрещены.
Неизвестная remote-операция остаётся unknown, доступный PR URL сохраняется.
Архивирование не отменяет отправленный push/create и не повторяет публикацию.

## Автоматический архив GitHub Issues

Каждый проход существующей синхронизации отдельно запрашивает ранее импортированные
issues, включая архивные. Фильтр — открытая issue с `ready-for-agent` в исходном
host/repository. Валидный ответ конкретной issue без метки или с `state=closed`
атомарно архивирует карточку независимо от стадии, локальных правок и результатов.
Затем контроллер отменяет очередь и инициирует остановку без ожидания callbacks.
Pending human requests и queued/sending chat отзываются. История, локальное описание,
редакции, завершённые runs, файлы, worktrees и PR сохраняются.

Отсутствие в списке, ошибка страницы, timeout, 404, некорректные данные, другая
issue/repository/host или pull request не доказывают несоответствие. Ошибка списка
не мешает применить отдельно подтверждённый ответ issue. Исходная issue не меняется.

SQLite v16 хранит `archive_source` (`manual` или `github-filter`) и `archive_reason`.
Миграция v15 признаёт прежний автоматический архив только по единственному событию
`task.archived` с причиной «Исходная GitHub issue закрыта.» и исходным номером issue,
без событий ручного удаления. Неоднозначные архивы остаются ручными.
Ручное архивирование имеет приоритет, в том числе во время запроса GitHub; действие
`/archive` может перевести автоматический архив в ручной.

Если валидный ответ снова подтверждает фильтр, автоматически архивированная карточка
возвращается с тем же ID, описанием и историей. Ручной архив не восстанавливается.
SSE обновляет доску, архив и открытую карточку; причина архива и состояние остановки
доступны в UI. Повторные одинаковые ответы не создают переходов или новых задач.
Несохранённый черновик описания хранится по ID задачи в текущей вкладке: его можно
скопировать в архиве и продолжить редактирование после разблокировки. Reload вкладки
не сохраняет черновики. При замене открытого представления фокус внутри карточки
переходит на её summary или заголовок; фокус вне карточки не переносится.

Восстановление меняет только видимость. Оно не ставит работу в очередь, не возвращает
отозванные сообщения/вопросы, не возобновляет pipeline или публикацию и не снимает
`deletion_state`, `stop_unverified`, `execution_unverified` и неизвестный исход
публикации. Карточка может вернуться до окончания остановки; её позднее завершение
не архивирует карточку повторно. Незавершённый callback продолжает удерживать slot.

На возвращённой карточке доступны повтор остановки и прежняя ручная сверка через
`/stop` без повторного архивирования. Явный успешный `/stop` разблокирует допустимые
действия только при подтверждённой остановке и отсутствии process-блокировок;
никакая работа при этом не запускается. Прерванная карточка без публикации возвращается
в Backlog с `run_state=idle`: пользователь может изменить описание или явно запустить
новую Spec в новом worktree. Старый pipeline не возобновляется. Прерванные runs остаются прерванными,
завершённые сохраняют результат, неизвестная публикация не сбрасывается.
История остановки остаётся в событиях. Дальнейший запуск требует отдельного действия
пользователя и существующих проверок. Видимость, происхождение архива и блокировки
сохраняются после restart.

Сверка из списка архива открывает стабильную страницу задачи. Восстановление по SSE
сохраняет открытый диалог, введённый текст и клавиатурный фокус. При смене версии
пользователь явно выбирает «Сверять актуальную версию» перед отправкой; старую версию
backend по-прежнему отклоняет. Reload вкладки не сохраняет текст сверки.

## Проверка

`npm run check` на Node.js 24. Process tests требуют доступа к read-only `ps`.
Regression tests покрывают старую NeedsHuman-задачу с неподтверждённой остановкой,
немедленное скрытие при незавершённом callback, сохранение scheduler slot,
request replay/version/ownership, read-only историю, два SSE клиента,
миграции v13/v15 и restart, повтор остановки и ручную сверку, снятие/возврат метки,
закрытие/открытие issue, защиту от неполных ответов, конкурентные изменения,
восстановление во время callback и запрет продолжения pipeline.
Клиентский regression test проверяет перенос фокуса при архивировании и разблокировке,
включая disabled-кнопку сверки и закрытый dialog, без захвата фокуса другой карточки.

Для GUI используйте отдельный backend и временную базу: проверьте отмену
подтверждения, архивирование из detail, предупреждение об остановке, архивную
историю, повтор остановки без ручной сверки и сохранение архива после reload.
Не используйте пользовательские карточки для smoke-проверки.
