# Остановка и архив задач

«Остановить» возвращает неархивную карточку в Backlog / idle, сохраняя требования,
редакции, результаты, chat, PR и worktrees. Новый запуск — отдельное действие:
новый run/session/worktree от актуальной target branch, обычная очередь и global
execution pause. Partial edits не переносятся. Архивирование независимо управляет
видимостью: Stop архивной карточки не восстанавливает её; поздний callback не
архивирует автоматически восстановленную карточку повторно.

Это осознанная замена прежнего требования обязательной ручной сверки всех
гипотетических потомков. Историческая неопределённость (`legacy_execution_unknown` / `stop_unverified`) без проверяемого процесса
не блокирует Backlog и изолированный новый цикл. Он означает неполноту диагностики,
а не доказанное активное исполнение; фиктивный scheduler slot из него не создаётся.

## Протокол

`POST /api/projects/:projectId/tasks/:taskId/stop` принимает `request_id` и
`state_version`, сохраняет auth, ownership, schema validation и replay. Транзакция
принятия увеличивает `execution_generation`, отзывает все прежние runs (`revoked`),
pending human requests и queued/sending chat. Отзыв постоянен: старые callbacks,
в том числе того же этапа и revision, не могут изменить новую попытку, применить
ответы/требования или запустить следующий этап. Старые ответы и delivered guidance
остаются историей и не включаются в prompt нового цикла.

Контроллер снимает queued jobs, запрашивает interrupt Codex turn, abort и остановку
известных title/agent process groups. TERM → KILL через 500 ms. Общая обработка
Stop ограничена 5 секундами, включая диагностику; обычный process deadline —
4 секунды с запасом для завершения карточки. HTTP completion и Backlog не являются
подтверждением exit. Состояние `execution_warning`, процессы и результат внешней
операции передаются клиентам через SSE. Повтор Stop может повторить остановку,
но replay старого `request_id` никогда не останавливает новый запуск.

Известные оставшиеся процессы продолжают удерживать scheduler slot и получать
KILL после возврата карточки. Slot освобождается только владельцем старого job
после завершения известных процессов/callbacks; новая попытка ждёт обычную очередь.
Если survivor подтверждён уже во время новой работы той же задачи, он учитывается
отдельно от её job: завершение одного не освобождает slot другого.
Неизвестная legacy execution не резервирует бессрочный slot. Reset результатов
и существующие destructive actions сохраняют дополнительные idle/process/remote
проверки: возврат карточки сам по себе не разрешает удалять данные под исполнением.

## Идентичность и restart

SQLite v21 хранит `execution_processes`: task, run, execution generation, PID, PGID, время старта из `ps`,
состояние связанной группы `running` / `exited` / `unknown` (включая потомков).
Выход конкретного лидера отдельно фиксируется в `process.exited`. Run содержит worktree, branch и Codex
thread/turn в diagnostic. Thread — история сессии, не доказательство активности.
Процессы и обнаруженные связанные группы регистрируются до сигналов. Подтверждённый
exit снимает относящуюся к известным процессам неопределённость.
Title-процессы без run ID сохраняют свою generation: Stop старой generation
восстанавливается независимо от новых runs. Для записей v20 без generation после
принятого Stop также продолжается остановка проверенных процессов.

После restart выполняется read-only census. Только совпавшая идентичность процесса
разрешает сигнал его группе и восстановление занятого slot. Переиспользованный
PID/PGID или недоступная идентичность дают `unknown`, а не подтверждённую остановку;
непроверенным старым PID сигналы не отправляются. Известная отменённая execution
снова останавливается, queued work не возобновляется. При недоступном `ps` диагностика
сохранённых identities повторяется; после подтверждения survivor занимает slot и
остановка продолжается. Незавершённый Stop оставляет
неархивную карточку в Backlog с предупреждением. `ps` не гарантирует обнаружение
потомка, потерявшего связь с родителем до census; UI утверждает только состояние
известного исполнения. Старые события и flags без идентичности показывают неполноту.

## Публикация

`publication_run_id` и `publication_generation`, PR identity и журнал `publication.remote-operation` связывают
push/create и их receipts со старым run. Перед каждой новой операцией проверяется
полномочие исполнения. После принятого Stop новая операция старого run запрещена;
уже отправленная может завершиться. Её in-flight/confirmed/unknown и найденный URL
сохраняются даже после отзыва обычных callbacks, без изменения стадии нового цикла.

Stop не очищает `pending`/`unknown`: pending становится unknown, подтверждённый PR
и URL сохраняются. Unknown запрещает повтор remote publication, включая новый run,
но разрешает Backlog и изолированную локальную работу. Reset также не снимает unknown.
Уже отправленные операции не откатываются; automatic retry, merge и закрытие issue
не выполняются.

## UI и совместимость

«Остановить» → «Останавливаем…» → Backlog. При оставшемся процессе или неизвестной
диагностике доступны предупреждение и «Повторить остановку». Статусы процессов и
публикации показаны словами; raw JSON находится в закрытых «Технических подробностях».
Обычный Stop не открывает подтверждение и не требует textarea. «Архивировать» —
отдельная кнопка с native dialog и клавиатурным управлением.

`/archive` сразу сохраняет manual visibility, затем останавливает execution.
Совместимый `/delete` сохраняет прежнее логическое архивирование. `deletion_state`
по-прежнему хранит stopping / failed / deleted для архивных карточек; после обычного
Stop блокировка снимается независимо от outcome. Необязательный `reconciliation`
сохранён только для совместимости редкой ручной диагностики и аудита; он не заменяет
проверку реально известных процессов и не очищает unknown publication.

GitHub sync архивирует только после валидного ответа конкретной issue, не отвечающей
фильтру open + `ready-for-agent`. Ошибка/404/отсутствие в списке не доказывают
несоответствие. `archive_source=github-filter` и `archive_reason` сохраняются;
восстановление фильтра меняет только видимость, без возобновления pipeline.
Manual archive имеет приоритет. История доступна через ownership-checked read-only API.

## Проверка

`npm run check` на Node.js 24; process tests требуют read-only `ps`. Проверяются
queued/running/title/chat Stop, TERM → KILL, deadline и сохранение slot, legacy flags,
restart/PID reuse, stale callbacks, новый worktree и сохранение partial edits,
publication boundaries, request replay, archive/reset и SSE. GUI smoke использует
отдельный backend и временную базу, без пользовательских карточек.
