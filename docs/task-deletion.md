# Удаление задач

Действие «Удалить» доступно в открытой карточке во всех стадиях. Отмена диалога
не вызывает API. Подтверждение вызывает `POST /api/projects/:projectId/tasks/:taskId/delete`
с `request_id` и `state_version`. Проверка проекта и версии предшествует любым
сигналам процессам; идентичный request replay возвращает сохранённый результат.

SQLite v12 сохраняет `deletion_state`: `stopping`, `failed`, `deleted`.
Сначала атомарно фиксируется намерение удаления, отзываются pending human requests
и queued/sending chat messages. Все действия и late callbacks блокируются.
`stopping` и `failed` остаются на доске; только `deleted` скрывается из snapshots.
История, файлы, worktrees, branches и существующий PR сохраняются.

Task execution и генерация заголовка владеют отдельными POSIX process groups.
Подготовка worktree, Codex и публикация наследуют process ownership
через AsyncLocalStorage. Перед сигналами read-only `ps` census находит дерево
потомков, включая их отдельные process groups. Удаление снимает queued jobs,
блокирует новые команды, посылает TERM всем принадлежащим задаче группам,
через 500 ms усиливает сигнал до KILL и ждёт исчезновения групп и завершения
callbacks. До остановки известных групп scheduler удерживает слот. Через 5 s без
подтверждения карточка получает ошибку; блокировка сохраняется. Повтор удаления
с новым request ID допускается после фактического завершения callbacks/процессов.

`ps` не доказывает отсутствие всех потомков: detached-процесс может осиротеть
между снимками дерева. Поэтому каждый зарегистрированный процесс (включая
генерацию заголовка) устанавливает сохраняемый `stop_unverified`. Завершение
лидера и исчезновение известных групп этот флаг не снимают. Удаление такой задачи
остаётся `failed`, даже если известные процессы остановлены; обычный повтор
не заменяет ручную сверку. Это консервативное ограничение действует и для
обычных завершившихся команд. Для автоматического доказательства потребуется
системное отслеживание потомков, сохраняющее ownership после reparenting.
Задачи, не запускавшие процессов, удаляются без ручной сверки.

Состояние исполнения сохраняется перед стартом процесса. После restart backend
не сигналит потенциально переиспользованным PID и не считает статус SQLite
доказательством остановки. Незавершённое удаление становится `failed`.
`GET /api/projects/:projectId/tasks/:taskId/deletion` возвращает PID/PGID,
время старта, branches, worktrees, SHAs и данные remote операций для ручной сверки.
При неподтверждённом исполнении человек проверяет эти данные
и отсутствие процессов/потомков. Затем в диалоге повторного удаления вводит
фактические наблюдения. Необязательный `reconciliation` сохраняется как
`task.stop-verified-by-human` с revision и state_version. Backend не выдаёт
это подтверждение за собственное доказательство остановки.

Публикация не повторяется автоматически. Отправленные push/create фиксируются
в events; подтверждённый URL сохраняется даже при последующей ошибке проверки.
Неизвестный remote результат остаётся `unknown` и сопровождается предупреждением.
Удаление не откатывает push и не меняет существующий PR.

## Проверка интерфейса

Проверять текущий Build worktree, без реального pipeline. В Node.js 24 выполните
`npm run build`, затем запустите отдельный backend с отдельным data directory:

```sh
SWFACTORY_DATA_DIR="$(mktemp -d)" PORT=4318 npm start
```

1. Откройте URL backend из терминала вручную в двух вкладках. Подключите тестовый
   репозиторий, добавьте задачу с узнаваемым названием, дождитесь заголовка
   (или убедитесь, что генерация неактивна). Pipeline не запускайте.
2. Откройте эту карточку в обеих вкладках. Нажмите «Удалить» в первой вкладке:
   проверьте название, остановку исполнения/публикации, сохранение истории,
   worktrees, branches, отчётов, логов, существующего PR и отсутствие восстановления.
   Отмените диалог, в том числе через Escape: карточка должна остаться в обеих вкладках.
3. Подтвердите удаление. При незавершённой остановке должен отображаться прогресс,
   остальные действия должны блокироваться. После успеха открытые карточки
   закрываются, обе вкладки показывают уведомление, карточка исчезает с доски.
   Для уже неактивной задачи операция может завершиться слишком быстро,
   чтобы визуально различить промежуточное состояние; укажите это в наблюдениях.
4. Перезапустите тестовый backend с тем же каталогом данных, откройте новый URL
   с bootstrap token: карточка должна оставаться отсутствующей.
5. Сообщите фактические наблюдения, проверенную версию worktree и любые отклонения.
   При этой реализации агент проверил в Chrome на изолированном backend:
   открытие подтверждения, фокус на «Отмена», отмену кнопкой и Escape,
   сохранение карточки после отмены. Удаление временной карточки выполнено через
   HTTP API: обе реальные вкладки закрыли detail и показали пустую доску и
   уведомление по SSE. Нажатие окончательного подтверждения пользователем
   остаётся сценарием ручного review. Остановка реальных процессов и detached
   потомков, гонки, restart и SSE дополнительно покрыты `test/deletion.test.ts`.

Regression review #44: реальные orphaned detached-потомки после завершения
лидера Spec и title сохраняют `failed` и `stop_unverified`; повтор без сверки
не скрывает карточку. После остановки потомка и записанной ручной сверки
удаление завершается. В Chrome на изолированном backend проверена ошибка
HTTP 500: dialog остаётся открыт, текст ошибки находится внутри его
accessibility tree, фон недоступен. VoiceOver отдельно не проверялся.
