# PRD: локальная Kanban-доска для coding agents

Дата: 12 октября 2026 года. Версия: 1.2.

Статус: согласованный состав MVP, оформленный по интервью. Технические предложения и непроверенные интеграции вынесены в [TECHNICAL_DESIGN.md](TECHNICAL_DESIGN.md). Код приложения ещё не написан.

Текущий scope: только Codex; приложение доводит задачу до создания PR/MR, а merge пользователь выполняет на GitHub/GitLab. Проверки качества — агентские reviews и существующий CI/CD проекта; отдельного backend test runner нет. Надёжное прерывание и восстановление дорабатываются после первого прототипа. Ранние документы о двух agent providers и merge gates не определяют текущий MVP.

## 1. Задача продукта

Дать одному разработчику локальное рабочее место, в котором он описывает задачи для своих репозиториев, запускает их выполнение агентами и принимает решения в карточках Kanban. Приложение сохраняет историю и состояние, организует реализацию, четыре ревью, создание PR/MR для последующего решения пользователя на GitHub/GitLab.

Основной интерфейс — Kanban в браузере. Backend работает локально на macOS независимо от вкладки. Пользователь подключает уже установленный и авторизованный Codex CLI; приложение создаёт собственные агентские сессии.

Приложение управляет фиксированным циклом обычным кодом. Отдельной LLM-сессии оркестратора нет. Модели создают спецификацию, реализуют задачу, проводят ревью и выдают содержательное решение APPROVE/ESCALATE.

## 2. Пользователь и ограничения первой версии

Один пользователь запускает приложение на своём Mac и работает с доверенными локальными репозиториями. Каждый экземпляр приложения независим. Подписки, установка CLI, доступ к Git remote и GitHub/GitLab принадлежат пользователю.

По последующему решению пользователя рабочие сессии Codex запускаются с полными разрешениями, как в Machinist, без подтверждения отдельных команд/изменений через UI. Это доверенное исполнение с правами пользователя ОС: worktree и инструкции не изолируют агента от других файлов или credentials. По контракту агент не выполняет merge. Это инструкция доверенному агенту, а не технический запрет прямого remote действия.

### Входит в MVP

- macOS; локальный backend и браузерный UI.
- Несколько локальных Git-репозиториев, общий Kanban и фильтр по проекту.
- Codex; выбор модели для ролей pipeline.
- Создание задачи из одного свободного описания; заголовок извлекает LLM.
- Фиксированный pipeline, четыре reviewer, отдельный approver.
- Worktree на задачу, создание PR/MR через GitHub/GitLab CLI.
- Три исполняемые задачи на всё приложение.
- Вопросы по требованиям и решения о продолжении/доработке непосредственно в карточке.
- Локальное сохранение задач и отчётов. Прерывание, отмена и восстановление — следующий этап после рабочего прототипа (§9).

### Не входит в MVP

- Linux, Windows, облачное исполнение, удалённые runners, командные аккаунты.
- YouTrack, Jira и другие task trackers.
- Claude Code, Grok CLI, Cursor CLI и другие агенты.
- Любой merge из приложения: автоматический и по кнопке; merge gates, queues/trains и классификатор допуска к auto-merge.
- Независимый запуск backend обязательных tests/lint/build для проверяемого проекта.
- Подключение произвольных уже открытых агентских сессий.
- Live approvals отдельных CLI tools и MCP permission bridge.
- Редактор pipeline, пользовательские стадии, визуальный конструктор процессов.
- Собственный diff viewer, редактор кода, терминал и построчные обсуждения.
- Herdr/MCP marketplace, универсальная plugin-платформа.
- Задачи, меняющие несколько репозиториев одновременно.
- Автоматическое извлечение OAuth-токенов, переключение на платный API или покупка дополнительных лимитов.

## 3. Подключение проекта и агентов

Пользователь выбирает локальный репозиторий, remote, целевую ветку и GitHub либо GitLab. Приложение проверяет доступность инструментов и объясняет проблемы настройки. Подключение проекта само по себе не запускает задачи и не меняет репозиторий.

В настройках проекта доступны назначения для Spec, Build, четырёх Review-ролей и Approve. Есть стартовые значения; пользователь может выбрать доступную ему модель Codex. Конкретная конфигурация сохраняется при запуске задачи. Изменение настроек проекта не должно незаметно переключать модель уже работающего агента.

Для работы агентов нужны инструкции проекта и, при наличии UI, запуска приложения. Они могут происходить из `AGENTS.md` и других принятых в репозитории документов; существенные неизвестные уточняются у пользователя. Агент может использовать команды проекта в ходе своей работы, но backend не запускает независимый набор обязательных проверок качества.

Любые staged, unstaged и untracked изменения, не исключённые Git ignore, в подключённом checkout блокируют начало новой задачи. Приложение показывает причину и список путей, но не делает commit, stash или discard за пользователя. Собственные незавершённые изменения в worktree прерванной задачи сохраняются и не считаются нарушением этого правила.

## 4. Создание и запуск задачи

1. Пользователь выбирает проект и вводит описание в свободной форме. Отдельного обязательного поля заголовка нет.
2. Карточка немедленно сохраняется в Backlog. LLM асинхронно формирует короткий информативный заголовок исключительно по описанию.
3. До получения заголовка показывается нейтральный идентификатор задачи. Ошибка генерации не уничтожает описание и не запускает реализацию.
4. Исходное описание сохраняется дословно и остаётся источником требований. Заголовок — навигационная метка, а не новая постановка.
5. Кнопка «Приступить к реализации» запускает preflight и ставит задачу в очередь. Если свободных слотов нет, карточка показывает ожидание.
6. Только после успешного preflight начинается Spec. Создание карточки и генерация заголовка сами по себе не разрешают редактирование проекта.

Пользователь может редактировать описание до запуска. После запуска уточнения проходят через явный вопрос в безопасной точке между запусками ролей. Изменение требований сохраняется новой редакцией и требует повторной работы затронутых ролей. Действие «Прервать и уточнить» добавляется вместе с поддержкой прерываний.

## 5. Kanban и фиксированный процесс

Колонки: **Backlog → Spec → Build → Review → Approve → PR/MR created**, отдельно **Needs human**.

Колонки описывают содержательный этап, а не состояние процесса. Очередь и лимит провайдера отображаются отдельными признаками; прерывание и отмена добавляются на следующем этапе. Drag-and-drop не запускает действия и не меняет стадии.

| Стадия      | Работа                                                                                   | Условие выхода                                                                 |
| ----------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Backlog     | Описание, автозаголовок, ожидание запуска                                                | Пользователь нажал кнопку; preflight пройден; выделен слот                     |
| Spec        | Изучение репозитория и проверяемые требования                                            | Валидная спецификация с acceptance criteria; существенные вопросы разрешены    |
| Build       | Реализация в worktree и проверки                                                         | Валидный отчёт READY агента; иначе блокировка |
| Review      | Code, security, UI, UX                                                                   | Получены четыре валидных результата для одной версии кода                      |
| Approve     | Содержательное решение агента; публикация после четырёх PASS | APPROVE либо разрешение человека по ESCALATE; создан PR/MR |
| PR/MR created | Создан PR/MR; доступны ссылка и отчёты | Конец автоматического pipeline; CI и merge — на платформе |
| Needs human | Вопрос, отклонённый approve или проблема исполнения                      | Явное действие пользователя и возвращение на сохранённый этап                  |

### Spec

Агент вправе самостоятельно выбирать технические детали в пределах описанной задачи. Существенные продуктовые решения и противоречия выносятся человеку. Вопрос должен объяснять, что неизвестно и как ответ повлияет на результат; по возможности предлагать варианты.

### Build и Review

Ревью выполняются четырьмя отдельными ролями. В первом прототипе они запускаются последовательно; параллельный запуск допустим как последующая оптимизация. Builder не продолжает правки, пока раунд не завершён. UI/UX допускают PASS с явным объяснением неприменимости; непроведённую необходимую проверку нельзя объявить PASS.

Любой CHANGES приводит к сбору всех замечаний раунда и доработке. После первой реализации разрешены максимум две автоматические доработки. Затем — Needs human с перечнем нерешённых замечаний. Сбой запуска или API не расходует бюджет доработок кода.

### Approve

После четырёх успешных reviews отдельный approver проверяет спецификацию, изменения, отчёты и причины риска, возвращая APPROVE или ESCALATE. APPROVE разрешает публикацию PR/MR, а не merge. При ESCALATE человек разрешает публикацию либо отправляет задачу на доработку. Текст «готово» или завершившийся процесс не считаются валидным verdict.

## 6. PR/MR, CI и merge

Приложение создаёт PR/MR со ссылками на результаты работы и завершает автоматический pipeline. Merge пользователь выполняет самостоятельно в GitHub/GitLab. Ни автоматического merge, ни кнопки merge в приложении нет.

Проверки качества выполняют агентские роли. Дополнительные детерминированные проверки выполняет существующий GitHub/GitLab CI/CD, если он настроен. Backend не запускает отдельный обязательный tests/lint/build runner и не объявляет агентский PASS эквивалентом пройденного CI.

Отсутствие, ожидание или ошибка CI не блокируют создание PR/MR. UI даёт ссылку на платформу; обязательный CI polling и интерпретация branch protection для прототипа не нужны. Состояние «PR/MR created» означает публикацию, а не готовность к merge.

Приложение не обещает актуальность base в момент будущего внешнего merge и не запускает цикл синхронизации/review при каждом изменении target. Если меняется код самой задачи до публикации, прежние reviews не подходят новой версии. Решения о дальнейшем обновлении ветки и merge остаются на платформе.

## 7. Решения человека

Карточка привлекает внимание визуальной меткой и отображает конкретную причину обращения. В MVP уведомления только внутри UI; системные push, email и мессенджеры не нужны.

| Вид обращения                 | Что видит пользователь                                                                      | Действие                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Вопрос по требованиям         | Контекст, варианты и рекомендуемый вариант, если он есть                                    | Выбрать ответ или написать свой                                       |
| Решение по эскалации approver | Причина, актуальные отчёты и затронутые файлы | Разрешить публикацию PR/MR либо отправить на доработку |
| Проблема окружения или лимита | Причина, сохранённое состояние и доступный следующий шаг                                    | Исправить условие и продолжить                                        |

Решение привязано к конкретному запросу и версии задачи. Двойное нажатие или устаревшая вкладка не должны запускать действие дважды. Вопрос завершает role run в checkpoint; ответ передаётся следующей попытке после выдачи слота. Отдельные команды и изменения файлов выполняются без permission prompt; управление прерыванием и отменой добавляется после первого прототипа.

Diff пользователь смотрит самостоятельно. UI показывает текстовые отчёты, список затронутых файлов, ссылки/пути к артефактам и PR/MR, но не содержит diff viewer. После публикации карточка содержит ссылку на созданный PR/MR.

## 8. Параллелизм и ожидания

Максимум три задачи одновременно исполняются агентами на любых этапах. Это не три на каждом этапе. Четыре reviewer одной задачи используют один слот задачи и в прототипе исполняются последовательно. При последующем включении параллельного review возможны до двенадцати reviewer-процессов.

Задача освобождает слот при ожидании человека или лимита, когда все её текущие исполнители завершились либо подтверждённо остановились. Если один reviewer спросил человека, а остальные ещё работают, приложение сначала дожидается завершения или подтверждённой остановки остальных; нельзя объявить слот свободным при продолжающейся фоновой работе.

После ответа карточка при необходимости показывает «Готова продолжить, ожидает слот». Ответ не должен незаметно создавать четвёртую исполняемую задачу.

## 9. Сохранение, остановка и восстановление

В первом прототипе локально сохраняются описание и редакции, заголовок, конфигурация запуска, отчёты, вопросы/ответы, Git SHA, worktree и ссылка на PR/MR. Только в памяти можно держать очередь активного процесса и handles дочерних процессов; сохранённая карточка и отчёты не должны зависеть от открытой вкладки.

Закрытие вкладки не останавливает backend. После перезапуска backend сохранённые карточки доступны, но незавершённые задачи сами не запускаются. Прототип не обещает продолжение с точки аварии; такие задачи отображаются как незавершённые с необходимостью ручной проверки. Их нельзя автоматически повторять в том же worktree при неизвестном состоянии прежнего процесса или публикации.

**После рабочего прототипа:** кнопки Interrupt/Cancel/Resume, остановка потомков CLI, session resume/fallback, восстановление неоднозначных push/create, crash/disk-full испытания. Эти проверки не блокируют начало разработки прототипа. Частичные изменения не удаляются и не откатываются автоматически.

| AC-13 | После четырёх PASS и APPROVE либо решения человека создаётся PR/MR через выбранный hosting CLI; URL сохранён в карточке |

| AC-18 | PR/MR created устанавливается после получения identity/URL созданного объекта; это не утверждение о CI success или merge |
| AC-19 | После restart сохранённые карточки и отчёты доступны; незавершённые задачи автоматически не запускаются |
| AC-20 | После прототипа: прерывание сохраняет частичные изменения; продолжение не применяет старый READY/PASS к изменённому коду |
| AC-21 | После прототипа: отмена прекращает исполнение без удаления истории и автоматического закрытия PR/MR |
| AC-22 | Логи, вопросы и отчёты доступны текстом; встроенного diff viewer, терминала и drag-and-drop переходов нет                              |

## 11. Признак готовности MVP

Первый прототип — одна реальная задача через Codex: описание → Spec → Build → четыре Review → Approve → созданный PR/MR, включая вопрос и ответ человека. Это первая вертикальная реализация, а не полная приёмка MVP.

MVP включает оставшиеся согласованные возможности доски и критерии выше, кроме явно отложенных AC-20/AC-21. Реальные интеграции GitHub и GitLab проверяются по мере появления доступного тестового remote; Claude для приёмки не нужен. Неоднозначная публикация в прототипе требует ручной сверки вместо автоматического retry.

Практические проверки и их приоритеты перечислены в [техническом дизайне](TECHNICAL_DESIGN.md#14-непроверенные-предположения-и-минимальные-проверки). Полное восстановление после сбоев развивается после первого рабочего прототипа.

## 12. Связь с исходным проектом

За основу взяты стадии, роли, файловые отчёты и ограничение доработок из [Software Factory](https://github.com/zazencodes/zazencodes-season-3/tree/555467c365e6750278efba09349369109f62f65f/src/software-factory-claude-code). Отличия согласованы: отдельное приложение, детерминированный controller, Codex adapter, Backlog, локальная база, создание PR/MR без merge и решения человека в UI.

В исходнике dirty checkout разрешён во время работы и проверяется перед локальным merge. В нашем MVP старт блокируется заранее, а основной checkout не используется для merge. Это намеренное отличие, а не утверждение о поведении исходника.
