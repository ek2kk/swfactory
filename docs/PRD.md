# PRD: локальная Kanban-доска для coding agents

Дата: 11 октября 2026 года. Версия: 1.0.

Статус: согласованный состав MVP, оформленный по интервью. Технические предложения и непроверенные интеграции вынесены в [TECHNICAL_DESIGN.md](TECHNICAL_DESIGN.md). Код приложения ещё не написан.

Этот документ учитывает последние решения пользователя. Ранние исследовательские заметки о Linux, отдельном Claude-оркестраторе, `codex exec` и сокращённом ревью не определяют состав MVP.

## 1. Задача продукта

Дать одному разработчику локальное рабочее место, в котором он описывает задачи для своих репозиториев, запускает их выполнение агентами и принимает решения в карточках Kanban. Приложение сохраняет историю и состояние, организует реализацию, четыре ревью, создание PR/MR и контролируемый merge.

Основной интерфейс — Kanban в браузере. Backend работает локально на macOS независимо от вкладки. Пользователь подключает уже установленные и авторизованные CLI; приложение создаёт собственные агентские сессии.

Приложение управляет фиксированным циклом обычным кодом. Отдельной LLM-сессии оркестратора нет. Модели создают спецификацию, реализуют задачу, проводят ревью и выдают содержательное решение APPROVE/ESCALATE.

## 2. Пользователь и ограничения первой версии

Один пользователь запускает приложение на своём Mac и работает с доверенными локальными репозиториями. Каждый экземпляр приложения независим. Подписки, установка CLI, доступ к Git remote и GitHub/GitLab принадлежат пользователю.

### Входит в MVP

- macOS; локальный backend и браузерный UI.
- Несколько локальных Git-репозиториев, общий Kanban и фильтр по проекту.
- Claude Code и Codex; выбор CLI и модели для ролей pipeline.
- Создание задачи из одного свободного описания; заголовок извлекает LLM.
- Фиксированный pipeline, четыре reviewer, отдельный approver.
- Worktree на задачу, PR/MR через GitHub/GitLab CLI, строгая политика merge.
- Три исполняемые задачи на всё приложение.
- Вопросы, решения и разрешения CLI непосредственно в карточке.
- Локальное сохранение, прерывание, отмена и ручное возобновление.

### Не входит в MVP

- Linux, Windows, облачное исполнение, удалённые runners, командные аккаунты.
- YouTrack, Jira и другие task trackers.
- Grok CLI, Cursor CLI и другие агенты.
- Подключение произвольных уже открытых агентских сессий.
- Редактор pipeline, пользовательские стадии, визуальный конструктор процессов.
- Собственный diff viewer, редактор кода, терминал и построчные обсуждения.
- Herdr/MCP marketplace, универсальная plugin-платформа.
- Задачи, меняющие несколько репозиториев одновременно.
- Автоматическое извлечение OAuth-токенов, переключение на платный API или покупка дополнительных лимитов.

## 3. Подключение проекта и агентов

Пользователь выбирает локальный репозиторий, remote, целевую ветку и GitHub либо GitLab. Приложение проверяет доступность инструментов и объясняет проблемы настройки. Подключение проекта само по себе не запускает задачи и не меняет репозиторий.

В настройках проекта доступны назначения для Spec, Build, четырёх Review-ролей и Approve. Есть стартовые значения; пользователь может выбрать поддерживаемый CLI и доступную ему модель. Конкретная конфигурация сохраняется при запуске задачи. Изменение настроек проекта не должно незаметно переключать модель уже работающего агента.

Для работоспособности проекта нужны инструкции установки, проверок и, при наличии UI, запуска приложения. Они могут происходить из `AGENTS.md`/`CLAUDE.md`; существенные неизвестные уточняются у пользователя. Эти файлы не заменяют структурированные настройки политик merge.

Любые staged, unstaged и untracked изменения, не исключённые Git ignore, в подключённом checkout блокируют начало новой задачи. Приложение показывает причину и список путей, но не делает commit, stash или discard за пользователя. Собственные незавершённые изменения в worktree прерванной задачи сохраняются и не считаются нарушением этого правила.

## 4. Создание и запуск задачи

1. Пользователь выбирает проект и вводит описание в свободной форме. Отдельного обязательного поля заголовка нет.
2. Карточка немедленно сохраняется в Backlog. LLM асинхронно формирует короткий информативный заголовок исключительно по описанию.
3. До получения заголовка показывается нейтральный идентификатор задачи. Ошибка генерации не уничтожает описание и не запускает реализацию.
4. Исходное описание сохраняется дословно и остаётся источником требований. Заголовок — навигационная метка, а не новая постановка.
5. Кнопка «Приступить к реализации» запускает preflight и ставит задачу в очередь. Если свободных слотов нет, карточка показывает ожидание.
6. Только после успешного preflight начинается Spec. Создание карточки и генерация заголовка сами по себе не разрешают редактирование проекта.

Пользователь может редактировать описание до запуска. После запуска уточнения проходят через явный вопрос либо действие «Прервать и уточнить»: новая редакция требований сохраняется, а затронутые spec/review/approval пересматриваются.

## 5. Kanban и фиксированный процесс

Колонки: **Backlog → Spec → Build → Review → Approve → Merged**, отдельно **Needs human**.

Колонки описывают содержательный этап, а не состояние процесса. Очередь, ожидание CI, лимит провайдера, прерывание и отмена отображаются отдельными признаками. Drag-and-drop не запускает действия и не меняет стадии.

| Стадия      | Работа                                                                                   | Условие выхода                                                                 |
| ----------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Backlog     | Описание, автозаголовок, ожидание запуска                                                | Пользователь нажал кнопку; preflight пройден; выделен слот                     |
| Spec        | Изучение репозитория и проверяемые требования                                            | Валидная спецификация с acceptance criteria; существенные вопросы разрешены    |
| Build       | Реализация в worktree и проверки                                                         | Отчёт READY и независимо зафиксированные результаты проверок; иначе блокировка |
| Review      | Code, security, UI, UX                                                                   | Получены четыре валидных результата для одной версии кода                      |
| Approve     | Создание/обновление PR/MR после reviews, CI, содержательное решение агента и merge gates | Подтверждённый remote merge либо решение/действие человека                     |
| Merged      | Результат включён в целевую ветку                                                        | Терминальное успешное состояние                                                |
| Needs human | Вопрос, разрешение CLI, отклонённый approve или проблема исполнения                      | Явное действие пользователя и возвращение на сохранённый этап                  |

### Spec

Агент вправе самостоятельно выбирать технические детали в пределах описанной задачи. Существенные продуктовые решения и противоречия выносятся человеку. Вопрос должен объяснять, что неизвестно и как ответ повлияет на результат; по возможности предлагать варианты.

### Build и Review

Ревью выполняются четырьмя отдельными ролями. Они могут работать параллельно, но builder не продолжает правки, пока раунд не завершён. UI/UX допускают PASS с явным объяснением неприменимости; непроведённую необходимую проверку нельзя объявить PASS.

Любой CHANGES приводит к сбору всех замечаний раунда и доработке. После первой реализации разрешены максимум две автоматические доработки. Затем — Needs human с перечнем нерешённых замечаний. Сбой запуска или API не расходует бюджет доработок кода.

### Approve

PR/MR создаётся после четырёх успешных reviews. Отдельный approver проверяет спецификацию, изменения, отчёты и причины риска, возвращая APPROVE или ESCALATE. Приложение дополнительно проверяет машинные условия. Текст «готово» или завершившийся процесс не считаются одобрением.

## 6. Политика merge

Автоматический merge выключен по умолчанию и включается отдельно для проекта. В MVP он допускается только для подтверждённых изменений документации и тестов. Неопределённая классификация и изменения production-кода требуют человека.

Сохраняются строгие эскалации для auth/permissions, payments, migrations, deploy/CI/build configuration, новых dependencies и существенных продуктовых допущений. Путь вида `tests/` или расширение `.md` сами по себе не доказывают низкий риск.

Для любого merge обязательны:

- Все четыре reviews PASS для актуальной версии кода.
- Пройденные проектные проверки и обязательный CI для актуального изменения.
- Отсутствие конфликтов и соблюдение правил remote, включая необходимые платформенные approvals.
- Актуальная проверка целевой ветки.
- APPROVE агента либо явное решение человека по выданной эскалации; человек не может кнопкой обойти обязательный CI или защиту ветки.

Если CI не настроен либо его требования нельзя достоверно установить, автоматический merge запрещён. Это объясняется человеку; отсутствие CI нельзя помечать как успешный CI. Приложение не реализует bypass. Если пользователь самостоятельно выполнит merge на платформе, приложение отражает подтверждённый факт и сохраняет историю собственного отказа.

Внутри одного репозитория merge выполняются последовательно. Если целевая ветка изменилась, приложение обновляет ветку задачи, повторяет проверки, все четыре reviews и Approve. Старое человеческое разрешение также становится неактуальным. Такая синхронизация не равна исправлению по замечаниям, но не может создавать бесконечный автоматический цикл: технический предел описан в дизайне.

## 7. Решения человека

Карточка привлекает внимание визуальной меткой и отображает конкретную причину обращения. В MVP уведомления только внутри UI; системные push, email и мессенджеры не нужны.

| Вид обращения                 | Что видит пользователь                                                                      | Действие                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Вопрос по требованиям         | Контекст, варианты и рекомендуемый вариант, если он есть                                    | Выбрать ответ или написать свой                                       |
| Подтверждение изменения/merge | Почему автоматическое продолжение запрещено, что нужно оценить, ссылки на артефакты и PR/MR | Разрешить продолжение/merge либо отправить на доработку с замечаниями |
| Разрешение CLI                | Запрашиваемое действие, команда/пути/доступ и причина                                       | Разрешить один раз, отклонить либо прервать задачу                    |
| Проблема окружения или лимита | Причина, сохранённое состояние и доступный следующий шаг                                    | Исправить условие и продолжить                                        |

Решение привязано к конкретному запросу и версии задачи. Двойное нажатие или устаревшая вкладка не должны запускать действие дважды. Отказ в одном действии CLI не равен отмене всей задачи: агент получает отказ; пользователь может отдельно прервать или отменить работу.

Diff пользователь смотрит самостоятельно. UI показывает текстовые отчёты, список затронутых файлов, ссылки/пути к артефактам и PR/MR, но не содержит diff viewer. В разрешении изменения должна быть ссылка на подробности предложенного действия, если их нельзя достаточно описать кратко.

## 8. Параллелизм и ожидания

Максимум три задачи одновременно исполняются агентами на любых этапах. Это не три на каждом этапе. Четыре reviewer одной задачи используют один слот задачи, поэтому возможны до двенадцати одновременно работающих reviewer-процессов.

Задача освобождает слот при ожидании человека, CI или лимита, когда все её текущие исполнители остановились либо дошли до безопасного ожидания. Если один reviewer спросил человека, а остальные ещё работают, приложение сначала приводит задачу к такому состоянию; нельзя объявить слот свободным при продолжающейся фоновой работе.

После ответа карточка при необходимости показывает «Готова продолжить, ожидает слот». Ответ не должен незаметно создавать четвёртую исполняемую задачу.

## 9. Сохранение, остановка и восстановление

Локально сохраняются описание и его редакции, LLM-заголовок, конфигурация запуска, spec, build/review/approve-отчёты, попытки, сообщения и решения человека, session IDs, Git SHA, worktree, PR/MR и события исполнения.

- **Закрытие вкладки:** работа продолжается; после открытия UI восстанавливает актуальную картину.
- **Прервать:** приложение останавливает принадлежащее задаче исполнение, сохраняет частичные изменения и возможность продолжения. Остановка не обещает откат уже выполненных действий.
- **Отменить:** задача исключается из исполнения, но история и результаты сохраняются. Remote PR/MR не закрывается автоматически; удаление ветки/worktree — отдельное явное действие.
- **Перезапуск backend:** данные восстанавливаются без автоматического возобновления задач. Пользователь нажимает «Продолжить».
- **Продолжить:** сначала проверяются процессы, worktree, артефакты и remote; затем используется прежняя сессия либо новая с сохранённым контекстом. Создание PR/MR и merge не повторяются вслепую.

Прерванные карточки остаются на последнем этапе с признаком состояния. Отменённые доступны в фильтре истории и исключены из обычной активной доски. Новые pipeline-стадии для этих признаков не добавляются.

## 10. Критерии приёмки

| ID    | Проверяемый сценарий и ожидаемый результат                                                                                             |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------- |
| AC-01 | UI запускается локально на macOS; его закрытие не останавливает запущенного агента                                                     |
| AC-02 | Подключены два проекта; общий вид показывает оба, фильтр оставляет задачи одного                                                       |
| AC-03 | Создание только из описания сохраняет карточку; LLM создаёт заголовок без изменения описания; сбой заголовка не теряет задачу          |
| AC-04 | До нажатия «Приступить к реализации» никакой агент не изменяет репозиторий                                                             |
| AC-05 | Staged, unstaged и неигнорируемый untracked файл блокируют старт; приложение ничего не исправляет автоматически                        |
| AC-06 | Задача использует отдельный worktree выбранной целевой ветки; основной checkout пользователя не изменяется                             |
| AC-07 | Для каждой роли можно выбрать Claude Code/Codex и модель; недоступная конфигурация даёт объяснимую ошибку без молчаливой замены        |
| AC-08 | До четырёх завершённых reviews одной версии кода нет перехода к PR/MR; один CHANGES запускает доработку только после завершения раунда |
| AC-09 | После двух автоматических доработок и оставшихся CHANGES задача требует человека                                                       |
| AC-10 | Существенный вопрос отображается в карточке; ответ сохраняется и возвращает задачу на нужный этап                                      |
| AC-11 | В отдельном проверочном сценарии каждого CLI запрос команды/изменения попадает в UI; разрешение и отказ адресуются правильному запросу |
| AC-12 | При занятых трёх слотах четвёртая задача ждёт; ответ на запрос не превышает лимит; ожидание всей задачи освобождает слот               |
| AC-13 | После PASS создаётся один PR/MR через выбранный hosting CLI; повторный запуск после неоднозначного результата не создаёт дубль         |
| AC-14 | Автоматический merge выключен по умолчанию; production-код, рискованный тест/документ или неизвестная классификация требуют человека   |
| AC-15 | Failed/pending/missing/неопределённый обязательный CI не позволяет приложению выполнить merge; ручная кнопка не обходит защиту ветки   |
| AC-16 | Разрешение человека дано в карточке; причина обращения и принятое решение доступны в истории                                           |
| AC-17 | После изменения целевой ветки проходят повторные проверки, четыре reviews и Approve; устаревшее разрешение не применяется              |
| AC-18 | Два merge одного проекта не выполняются одновременно; успех подтверждается remote, а не только exit code CLI                           |
| AC-19 | После остановки backend карточки и артефакты восстановлены; ни одна незавершённая задача не стартует без кнопки пользователя           |
| AC-20 | Прерывание во время записи кода сохраняет изменения; продолжение не применяет старый READY или approval к новой попытке                |
| AC-21 | Отмена прекращает исполнение без удаления истории и без автоматического закрытия PR/MR                                                 |
| AC-22 | Логи, вопросы и отчёты доступны текстом; встроенного diff viewer, терминала и drag-and-drop переходов нет                              |
| AC-23 | Кнопки и формы работают с клавиатуры; ожидание/ошибка/нужное действие различимы текстом, а не только цветом                            |

## 11. Признак готовности MVP

MVP готов после прохождения критериев выше на macOS, включая реальные проверки двух agent adapters и двух hosting adapters в тестовых репозиториях. Красивой доски с имитируемыми агентами для готовности недостаточно.

Практические проверки протоколов перечислены в [техническом дизайне](TECHNICAL_DESIGN.md#14-непроверенные-предположения-и-минимальные-проверки). Если одна из них не проходит, это блокер заявленной функции, а не основание молча упростить согласованный MVP.

## 12. Связь с исходным проектом

За основу взяты стадии, роли, файловые отчёты и ограничение доработок из [Software Factory](https://github.com/zazencodes/zazencodes-season-3/tree/555467c365e6750278efba09349369109f62f65f/src/software-factory-claude-code). Отличия согласованы: отдельное приложение, детерминированный controller, multi-provider adapters, Backlog, локальная база, PR/MR, строгие merge gates и решения человека в UI.

В исходнике dirty checkout разрешён во время работы и проверяется перед локальным merge. В нашем MVP старт блокируется заранее, а основной checkout не используется для merge. Это намеренное отличие, а не утверждение о поведении исходника.
