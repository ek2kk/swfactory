# SW Factory

Локальная Kanban-доска для macOS: подключить Git-проект, сохранить задачу
с автозаголовком, получить Spec и реализацию выбранными моделями Codex в отдельном
worktree. После готовой Spec Build автоматически попадает в общую очередь.
Кнопка «Запустить Build» доступна для Spec, сохранённых до обновления или при остановке backend.
Проверенный READY с commit запускает четыре последовательных Review. Четыре актуальных PASS автоматически запускают отдельную сессию Approve.

## Запуск

Нужны Node.js **24.21.0 LTS** (см. `.nvmrc`), npm, Git и авторизованный `gh`
для GitHub либо `glab` для GitLab, а также авторизованный Codex CLI (`codex login`).
Адаптер проверяется с Codex 0.160.1. Если native addon не установился готовым
бинарником, для сборки `better-sqlite3` нужны Xcode Command Line Tools.

```sh
nvm install
nvm use
npm ci
npm run check
npm start
```

Откройте URL, напечатанный backend. Bootstrap token передаётся во fragment,
удаляется из адресной строки и обменивается на HttpOnly/SameSite session cookie.
После restart откройте новый URL из терминала. Не публикуйте этот URL.
Backend работает отдельным процессом: закрытие браузерной вкладки его не
останавливает. Остановка — Ctrl+C в терминале: backend ждёт текущие runs, новые из очереди
не запускает. Архивирование отменяет очередь и останавливает известные группы процессов; автозапуска при входе нет.

По умолчанию: `http://127.0.0.1:4317`, данные —
`~/Library/Application Support/AgentKanban/`. Можно задать `PORT` и
`SWFACTORY_DATA_DIR` перед запуском. Не выбирайте checkout проекта как data directory.
Один data directory может принадлежать только одному backend, даже на разных
портах. Настройки проектов, карточки, редакции и события хранятся в `state.sqlite`;
`owner.sqlite` удерживает process-lifetime exclusive lock. Не удаляйте его при
работающем backend. Данные и их история автоматически не удаляются.

## Подключение и карточки

1. Нажмите «Выбрать папку…» для выбора checkout через системный диалог macOS
   либо введите абсолютный путь вручную. Диалог открывается на машине backend;
   отмена сохраняет введённые поля. Укажите remote, target branch и hosting,
   затем нажмите «Подключить». Для self-hosted GitHub/GitLab выберите тип hosting явно.
2. Приложение читает Git root, common-dir, remote и **локальную remote-tracking
   target branch**, затем проверяет CLI auth для host из remote. Оно не делает
   fetch, checkout, stash, commit и не запускает агентов. Если target отсутствует,
   самостоятельно выполните `git fetch <remote>` в своём checkout и повторите.
   HTTPS remote со встроенными credentials не принимаются — используйте CLI auth.
3. Добавьте описание: пробелы и переносы сохраняются дословно. Заголовок не нужен;
   карточка показывает нейтральный ID. Редактирование создаёт новую редакцию,
   предыдущие доступны в истории. Чужая новая редакция блокирует устаревшую запись.

Диалог выбора папки принадлежит Finder и открывается поверх других окон.
При первом использовании macOS может запросить разрешение Automation для backend
на управление Finder. Если разрешение не выдано, доступен ручной ввод пути.
Через две минуты ожидание диалога завершается ошибкой, форму можно использовать снова.

## Страница задачи и чат

«Открыть задачу ↗» открывает отдельную страницу `?task=<id>` на всю рабочую область.
Вкладки: Обзор, Spec, Build, четыре Review и Approve. На вкладках этапов — все
попытки, сообщения агента, раскрываемые вызовы инструментов и сохранённые отчёты.
Обязательные вопросы и решения о публикации остаются на вкладке «Обзор».
Доска использует тот же SSE snapshot. Открытие страницы не запускает работу.
Возврат кнопкой или browser Back сохраняет фильтр, прокрутку доски и черновики форм;
повторное открытие сохраняет выбранную вкладку. Несохранённые черновики живут до reload.

В поле сообщения доступны два режима:

- **Указание в рамках текущей Spec**: во время работы передаётся в активный
  `turn/steer`, между запусками ждёт следующий turn. «Принято активным turn»
  означает подтверждение CLI, а не гарантию выполнения указания. Обязательные
  вопросы и approvals этим сообщением не закрываются. Доставленные указания
  передаются в контекст следующих ролей той же редакции.
- **Изменение требований**: добавляется к описанию после завершения текущего этапа
  (либо сразу между запусками), создаёт новую редакцию, отзывает старые вопросы и
  проверки. Задача возвращается в Backlog; новую Spec запускает пользователь.
  Предыдущие worktree и отчёты сохраняются. Это не немедленная остановка агента.

Чат сохраняется в SQLite. Повтор HTTP-запроса не дублирует сообщение. Отправка,
подтверждение, отказ и неизвестная доставка различаются; неизвестная доставка
после потери соединения/restart автоматически не повторяется. После прерывания
исполнения или начала публикации отправка заблокирована до ручной сверки.

Рабочие роли используют `codex app-server --listen stdio://` с отдельным thread на
run; Title и неинтерактивные вызовы сохраняют `codex exec`. Проверено на Codex
**0.160.1**: `initialize → thread/start → turn/start → turn/steer`, подтверждён тот же
turn и маркер из сообщения в финальном результате. Протокол описан в
[OpenAI Docs](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn).
Повторить реальный smoke на пустом временном Git-репозитории (расходует доступ к модели):

```sh
npx tsx scripts/smoke-steering.ts
```

История читает redacted JSONL порциями; текст показывается после завершения
сообщения CLI, инструменты — при старте и завершении. Посимвольные deltas не
показываются: секрет может быть разделён между ними. Старые `codex exec` логи
поддерживаются, но логи без подтверждённой redaction доступны только локально.

## Архивирование задачи

«Архивировать» сразу скрывает карточку с доски, блокирует новые действия и
публикацию, снимает очередь и пытается остановить известные процессы.
Это не подтверждение остановки всех потомков. При неподтверждённой остановке
карточка остаётся в архиве с предупреждением; ручная сверка для скрытия не нужна.

В разделе «Архив» доступны история описания, сообщения, отчёты и логи,
данные процессов и remote-операций. «Остановить исполнение / сверить» повторяет
остановку; фактическую ручную сверку можно записать отдельно. После restart
старым PID сигналы не отправляются. Архивирование не снимает `stop_unverified`
и не освобождает слот работающего callback или известной группы процессов.
Worktrees, branches и существующие PR сохраняются. Уже отправленные remote
операции не откатываются и не повторяются. Восстановления карточки в UI нет.
Подробнее: [архив и остановка](docs/task-deletion.md).

## Несколько проектов

Подключите каждый независимый checkout отдельно. Linked worktrees одного Git
common-dir считаются одним проектом и повторно не подключаются. Доска показывает
все проекты; фильтр «Проект» оставляет карточки выбранного и обновляет счётчик.
Host, repository и checkout помогают различать одинаковые имена и независимые clones.

GitHub issues импортируются при старте backend и сразу после подключения
GitHub-проекта: открытые issues с label `ready-for-agent`, без pull requests.
Затем каждый GitHub-проект опрашивается в фоне через 60 секунд после завершения
предыдущего прохода, в том числе после ошибки. Проекты опрашиваются независимо,
без параллельных проходов одного проекта, независимо от открытой вкладки и агентских задач.
Карточки и безопасные ошибки приходят в UI через SSE без reload; полностью успешный
проход очищает ошибки своего проекта. При закрытии backend таймеры и запросы
отменяются, импорт завершается до закрытия базы.

Проект в форме «Новая задача» выбирается отдельно от фильтра доски. Настройки
моделей и инструкций сохраняются для каждого проекта; изменение влияет только
на новые старты Spec. Уже запущенная задача, её Build и ответы на вопросы сохраняют
конфигурацию старта. Remote и target задаются при подключении проекта.
Общая FIFO-очередь ограничена тремя исполняемыми задачами на всё приложение,
включая Title и все проекты. Четыре Review выполняются последовательно, а не
занимают четыре слота. Карточка показывает «В очереди · ожидает слот» отдельно
от стадии. Preflight нового запуска выполняется после получения слота, поэтому
изменения checkout за время ожидания тоже блокируют старт. Для продолжений
проверяется существующий worktree, включая незавершённый merge/rebase даже при
чистом status и неизменном HEAD; основной checkout может содержать работу пользователя.

Ответ на вопрос сохраняется сразу, продолжение становится в конец общей очереди.
Слот освобождается после завершения исполнителя, а не при получении промежуточного
события или отправке abort. После restart очередь и незавершённые runs отмечаются
interrupted и автоматически не запускаются.

`test/spec.test.ts` проверяет лимит между двумя проектами, изменение checkout
в очереди и сохранение ответа при трёх занятых слотах с FIFO-продолжением.
Там же проверяются совместные слоты Title/Spec, ожидание завершения после abort
и restart без запуска; `test/review.test.ts` проверяет последовательность четырёх ролей.

## Каталог моделей Codex

У каждой рабочей роли есть dropdown с названием и точным model ID, а также
«Другая модель…» для ручного ввода. Обновление списка не меняет назначения и
несохранённые правки. Модель, отсутствующая в каталоге, остаётся выбранной.

Рядом выбирается «Глубина рассуждений» отдельно для каждой роли. Варианты и их
порядок берутся из `supportedReasoningEfforts` выбранной модели, рекомендация —
из `defaultReasoningEffort`. Набор уровней не зашит в приложение. «По умолчанию
Codex» не передаёт override и сохраняет прежнее поведение; при смене модели
выбор сбрасывается на этот вариант. Для модели без метаданных новые уровни
выбрать нельзя, но сохранённое значение не теряется при обновлении каталога.

Необязательный `reasoning_efforts` сохраняется в project settings и фиксируется
в конфигурации запуска вместе с моделями. Изменения настроек не затрагивают
существующие запуски; их параметры видны в карточке. API проверяет новые пары
model/effort по каталогу, а неизменённые настройки разрешает сохранять при его
недоступности. Кеш может устареть; ошибка Codex не приводит к скрытой подмене.
App-server получает `turn/start.effort`, режим `codex exec` —
`-c model_reasoning_effort="..."`. Старые настройки и записи запусков работают
без миграции. Сейчас это настройка только рабочего Codex harness; генерация
автозаголовка использует собственные настройки CLI.

Backend использует `codex app-server` → `initialize` → `model/list` (с пагинацией),
из checkout проекта, без запуска thread/turn и inference. Механизм проверен на
Codex CLI 0.160.1; контракт описан в [OpenAI App Server docs](https://learn.chatgpt.com/docs/app-server).
Каталог может быть кеширован самим Codex и не является проверкой entitlement.
Ошибку исполнения `model_unavailable` по-прежнему обрабатывает существующий runner.

Discovery ограничен 10 секундами, после чего используется последний успешный
каталог из `models-<projectId>.json` в data directory. При отсутствии корректного
кеша используются уникальные `defaultModels`. UI показывает источник, время
последнего успеха и ошибку. Кеш разделён по проектам, хранит ID/названия и уровни reasoning effort
с описаниями и значением по умолчанию; обновляется атомарно. После смены аккаунта или конфигурации нажмите «Обновить
список моделей»; старый кеш не гарантирует доступность модели новому аккаунту.

Для проверки fallback без реального pipeline: запустите отдельный backend с
временным data directory, подключите проект и получите список; остановите backend,
затем запустите с тем же каталогом и тестовым `codex` в начале PATH, который
завершает `app-server` с ненулевым кодом. Источник должен стать «последний успешный
каталог». С новым data directory источник будет «встроенные настройки».
Автоматически эти сценарии проверяет `test/models.test.ts`.

## Запуск Spec

1. В «Модели и инструкции» задайте модели для Spec, Build, четырёх Review и
   Approve, а также дополнительные инструкции проекта. Стартовое значение —
   `gpt-6.1-sol`; это не обещание доступности в вашей подписке. Модель передаётся
   CLI явно и не заменяется при ошибке. Настройки и их revision фиксируются при старте.
2. Нажмите «Приступить к реализации». FIFO исполняет до трёх задач одновременно.
   Preflight блокирует staged, unstaged, неигнорируемые untracked изменения,
   незавершённый merge/rebase, изменившийся checkout или remote. Причины и пути
   видны в карточке запуска. После отказа preflight можно исправить checkout и
   явно повторить старт; новый request создаёт новую попытку.
3. Fetch выбранной remote target branch сохраняет SHA в отдельном ref. Branch
   `swfactory/<task-id>/<run-id>` и worktree создаются от этого SHA: неопубликованные
   локальные commits не подмешиваются. Основной checkout не переключается;
   stash/reset/автоматического исправления нет.
4. Spec получает описание, инструкции проекта, task/run/revision/base и указание
   читать применимые AGENTS.md в worktree. Только полный успешный JSONL stream,
   валидный structured result и неизменившийся Git state допускают READY → Build.
   NEEDS_INPUT завершает run и сохраняет вопросы в SQLite и отчёте. Карточка
   Needs human показывает контекст, влияние, варианты и свободный ввод. После
   всех обязательных ответов запускается новая попытка Spec с сохранённым контекстом.

Рабочий Codex app-server получает `approvalPolicy: "never"` и
`sandbox: "danger-full-access"`: без permission prompts и с full access. Worktree и инструкции **не являются sandbox**.
Spec запрещено менять source, создавать commits, публиковать или выполнять merge.
После неизвестного исхода исполнения требуется ручная сверка; частичные файлы не удаляются.
Известно завершившийся сбой можно повторить с сохранением истории и проверкой worktree.

SQLite хранит runs и решения, `artifacts/<run-id>/` — input/schema/result JSON,
report.md, events.jsonl и stderr.log; `worktrees/<project-id>/<run-id>/` — рабочие
деревья. Отчёт доступен через task/run ID, без произвольного пути и symlink escape.
Локальные process logs доступны в карточке Run порциями по 64 KiB через авторизованный
endpoint по task/run ID. Объём
логов ограничен 32 MiB на run, превышение останавливает процесс и блокирует переход.
Артефакты и worktrees автоматически не удаляются.

Dirty checkout допускается при подключении, но блокирует старт. Linked worktrees
одного common-dir считаются одним проектом. Проверка CLI auth не доказывает права
push; Spec не публикует изменения и не проверяет права будущей публикации.

## Проверки и границы

`npm run check` запускает тесты приложения, TypeScript и production build.
Проверяются rollback состояния/события, idempotency и stale state, редакции,
принадлежность карточки проекту, CSRF/Origin/Host, bootstrap auth, SSE replay и
snapshot, запрет второго владельца в другом процессе, restart/interrupted и
read-only Git inspection в одноразовом dirty checkout с linked worktree.

Browser UI получает данные приложения и сохранённый отчёт: provider credentials и CLI stderr не
передаются. Текст выводится как текст, без HTML. API произвольных файлов отсутствует; отчёты проверяют принадлежность task/project/run. UI обслуживается тем же
Fastify origin; Vite используется для сборки, отдельный dev server не требуется.

Не реализованы публикация GitLab, resume/cancel, backup/restore и crash/disk-full
испытания. Никакого автоматического retry незавершённого исполнения после restart:
состояния queued/running/waiting помечаются interrupted с сохранением истории.
Реальная GitLab-интеграция требует отдельного тестового remote; в этом срезе
формирование команд проверяется локально, реальные GitLab-права не заявляются.

Дополнительные тесты Spec: Git preflight и remote SHA на локальном bare remote,
изоляция локальных commits, три слота, immutable model config, READY/NEEDS_INPUT,
ошибки процесса/stream/schema, изменение source, rollback события и отказ записи
артефакта, start replay/ownership/version, migration v1/v2 → v3 и symlink escape.
Контракт structured output сверялся с [официальным примером Codex](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex)
и локальным `codex exec --help`.

Реальная проверка 12 октября 2026: Codex 0.160.1 / `gpt-6.1-sol` подготовил
READY через весь Spec controller на одноразовом локальном bare remote; отчёт
сохранён, stage=Build, source чистый. Отдельный smoke адаптера подтвердил запись
proof.txt в full-access режиме. Browser QA не выполнена: в среде проверки нет
подключённого браузера. Реальные GitHub/GitLab remote операции этим smoke не покрыты.

## Автозаголовки (срез 2)

После сохранения описания начинается title run. Редактирование очищает прежний
заголовок и ставит новую редакцию в очередь; ответ для старой редакции отбрасывается.
Три слота общие с рабочими задачами. Ошибки CLI, невалидный результат и timeout
(120 секунд) сохраняют карточку и историю; повторный HTTP request не запускает
повторную генерацию. После restart pending/running становятся interrupted без retry.
Фоновый заголовок не меняет `state_version` пользовательского описания: редактор
не теряет возможность сохранить черновик из-за ответа Codex.

Title mode получает только описание через stdin, работает из отдельного временного
каталога с read-only sandbox, без shell, web search, apps, plugins, hooks и
пользовательского config. Авторизация остаётся штатной CLI; модель — default CLI
без fallback. Текст и stderr CLI не отправляются в браузер. Настройки рабочего
проекта и дополнительные инструкции не участвуют в генерации заголовка.

Title и Spec используют одну FIFO-очередь и максимум три активные задачи. Старт
Spec атомарно отменяет pending title; активному Title CLI отправляется SIGTERM,
через секунду при необходимости SIGKILL. Слот освобождается только после `close`
процесса. Spec получает недостающий заголовок; готовый заголовок не заменяется.
Заголовок, завершение Spec и события сохраняются одной транзакцией после отчёта.
Полная остановка потомков и recovery остаются вне прототипа.

SQLite schema v3 обновляет v1 и обе прежние разновидности v2 (Title/Spec), сохраняя
описания, заголовки, runs и настройки. Старые карточки не запускаются автоматически.

Проверка реального CLI (тратит запрос к модели):

```sh
node --import tsx scripts/title-smoke.ts
```

12 октября 2026 smoke на macOS с Codex 0.160.1 вернул «Добавить экспорт отчётов
в CSV». Одноразовый Git repo, sentinel-файл и Git status остались неизменными,
хотя описание требовало изменить файл по абсолютному пути. Проверялся реальный
adapter приложения. Это проверка конкретного title mode, не всего pipeline.

После интеграции Title/Spec повторный реальный smoke 12 октября 2026 подтвердил
READY → сохранённый заголовок → Build при чистом source. `npm run check`: 43 теста,
включая ожидание CLI close, принудительную остановку и общий лимит Title/Spec.

## Вопросы и ответы (срез 4)

Варианты не выбираются автоматически. Все вопросы одного результата показаны
вместе; ответ сохраняется один раз вместе с событием и постановкой продолжения
в очередь. Повтор HTTP request не создаёт второй run; чужие, отозванные и устаревшие
запросы отклоняются. Новая попытка Spec использует прежние worktree, base SHA,
настройки и все предыдущие результаты/ответы текущей редакции. Git state проверяется
до и после исполнения. При продолжении идентичность репозитория (common dir и
remote) проверяется из worktree задачи; изменения в основном checkout не мешают
ответу. Проверка чистоты основного checkout выполняется при первом запуске. Ответ не является автоматической доработкой и не расходует
repair budget; Approve проверяет эту же версию после четырёх PASS.

Для изменения требований используйте «Редактировать» в ожидающей карточке или
после готовой Spec. Новая редакция отзывает открытые вопросы и возвращает задачу
в Backlog. Старые отчёты остаются в истории с отметкой «Неактуальна». Обычный ответ
не меняет редакцию и сохраняет применимость результатов.

Закрытие вкладки не теряет вопросы. После restart ответ можно сохранить, но
interrupted не запускается: сначала нужна ручная сверка, recovery UI пока нет.
SQLite v4 добавляет human_requests и связь попыток, сохраняя данные v1–v3.
Вопросы старых runs из v3 остаются текстом в исторических отчётах и требуют ручной
сверки; структурированные поля для них не выдумываются при миграции.

Проверки среза: цикл из двух вопросов до READY на локальном Git remote,
обязательные ответы, replay/ownership/version/schema/CSRF, отзыв при изменении
требований, restart без запуска, изменённый worktree и rollback событий/очереди.
Новый цикл с реальным Codex и интерактивная browser QA не выполнялись.

## Build (срез 5)

Build использует описание текущей редакции, готовую Spec, AGENTS.md и конфигурацию,
зафиксированную при старте задачи. Он делит FIFO и лимит трёх задач с Title/Spec.
READY содержит точные `changed_paths`, действия и фактические проверки. BLOCKED,
невалидный результат и ошибка CLI не переводят задачу в Review.

Coordinator проверяет branch, линейную историю от base и совпадение заявленных
путей с Git. Он проверяет содержимое до staging, добавляет только explicit literal
paths и сверяет дерево commit; blanket staging не используется. Существующие
builder commits проверяются, включая промежуточные версии файлов, и не дублируются.
Commit coordinator выполняется без Git hooks, чтобы hooks не меняли проверенное
дерево. Проектные проверки выполняет Build, их результат сохраняется в отчёте.
Перед Review сохраняются base/head SHA и подтверждается чистота source tree.
Артефакты остаются в data directory вне source; основной checkout не изменяется.

NEEDS_INPUT использует общую форму вопросов. Частичные правки сохраняются;
продолжение идёт в прежнем worktree после сверки hash файлов, index, branch и HEAD.
Внешнее изменение блокирует продолжение. После restart сохраняются данные и правки,
но незавершённая работа становится interrupted и не запускается автоматически.
SQLite v5 добавляет роль запуска, head SHA и hash source без удаления старых данных.

Консервативные ограничения: symlink/submodule/специальные файлы, файлы больше 2 MiB,
скрытые index entries, нелинейная история и неоднозначные пути требуют ручной сверки.
Проверка имён и сигнатур секретов может давать false positives и не заменяет полный
secret scanner. Worktree и инструкции ролей не являются sandbox для full-access Codex.

Реальная проверка adapter и coordinator (использует запрос к модели):

```sh
node --import tsx scripts/build-smoke.ts
```

Smoke создаёт одноразовый repo, требует реального изменения `hello.txt` и
структурированного READY, затем проверяет commit и чистое дерево. Артефакты и repo
сохраняются по напечатанному пути в `/private/tmp` для ручной проверки.

12 октября 2026 реальный smoke на macOS с `gpt-6.1-sol` подтвердил file edit,
READY, commit coordinator и чистое дерево. Интерактивная browser QA не выполнялась.

## Review (срез 6)

После Build автоматически выполняются Code → Security → UI → UX в отдельных
Codex sessions. Каждая роль получает сохранённую Spec, редакцию требований,
base/head и frozen model settings. Отчёты доступны отдельно в карточке, включая
findings, evidence и applicability. UI/UX PASS по неприменимости требует объяснения;
необходимая недоступная проверка должна приводить к NEEDS_INPUT или BLOCKED.

CHANGES не запускает Build внутри раунда: остальные reviewers завершают проверки.
Вопрос приостанавливает очередь ролей; ответ запускает новую сессию той же роли
с сохранёнными ответами. После restart ожидание ответа сохраняется, если завершение
исполнения подтверждено. Отправка ответа продолжает ту же роль после проверок
worktree. Для старых прерванных задач с уже сохранёнными ответами доступно
«Продолжить с сохранёнными ответами». Сам restart запуск не создаёт.
CHANGES в завершённом раунде запускает доработку в пределах бюджета двух попыток;
после исчерпания бюджета требуется человек. Только четыре PASS одной версии дают Approve.

Backend проверяет branch, repository, чистоту source и его hash до и после каждой
роли; изменение source сохраняется и делает прежние reviews неактуальными.
Сохранённый раунд, включая остановленный или ожидающий ответа, повторно проверяется при snapshot/reconnect; постоянного filesystem
watcher нет. Запуск Approve повторяет `verifyReviewSource` и проверяет
`reviewPasses` непосредственно перед исполнением. Worktree/instructions не являются sandbox.
SQLite v6 сохраняет round/Spec bindings и восстанавливает Spec binding прежних Build.

## Approve и решение человека

После четырёх PASS approver получает Spec, immutable base/head SHA, доступ к
изменениям в worktree и все четыре отчёта в новой сессии. Только структурированный APPROVE разрешает публикацию PR/MR;
после этого доступна кнопка «Опубликовать GitHub PR». Merge приложением запрещён.

ESCALATE показывает риски, затронутые файлы и ссылки на отчёты. Человек может
разрешить публикацию этой версии либо указать причину и отправить её в Build.
Решение сохраняется с request/run ID, редакцией, Spec и head SHA. Повторный submit
не запускает вторую работу. Доработка и изменение source аннулируют зависимые
reviews и разрешения; перед решением и после Approve Git state проверяется снова.
NEEDS_INPUT использует общий вопрос/ответ. После restart незавершённая работа
не продолжается автоматически и требует ручной сверки.


## Публикация GitHub

Кнопка публикации проверяет четыре актуальных PASS и APPROVE либо сохранённое
решение человека по ESCALATE. Backend повторно проверяет source перед push и create,
ищет PR по branch, target и task marker во всех состояниях. Существующий PR принимается
только с точными repository, head SHA, branch, target и marker; закрытый или изменённый
PR требует ручной сверки. Push отправляет одобренный SHA без force; отдельный push URL запрещён.

Стадия PR/MR created и ссылка появляются только после подтверждения объекта через
GitHub API. CI не проверяется и не объявляется PASS: его отсутствие, ожидание или
ошибка не блокируют создание. Merge, auto-merge и синхронизация с изменившимся target
не выполняются. Branch и worktree сохраняются.

Попытка записывается до сетевых действий. Повтор запроса не создаёт вторую работу.
При ошибке, потере ответа или restart во время публикации карточка показывает
неизвестный исход и запрещает retry: вручную сверяйте GitHub, task marker и source
branch из отчёта. Автоматической reconciliation или кнопки повторной публикации нет.
SQLite v8 сохраняет статус публикации, номер и URL PR вместе с событиями.

Ручной real smoke: `node --import tsx scripts/smoke-github.ts`. Скрипт использует
авторизованные Codex/gh, private `ek2kk/swfactory-smoke` из checkout
`/tmp/swfactory-real-smoke`, создаёт только toy CLI `hello.mjs`, его `node:test` и README.
Он проходит настоящий вопрос/ответ и pipeline до PR; source приложения не копируется.
Evidence сохраняется в `/tmp/swfactory-real-evidence-2`, remote/ветки не удаляются.
12 октября 2026 реальный smoke с `gpt-6.1-sol` прошёл Spec NEEDS_INPUT → ответ →
Spec READY → Build READY → Code/Security/UI/UX PASS → APPROVE → подтверждённый
[GitHub PR #1](https://github.com/ek2kk/swfactory-smoke/pull/1).
Одобренный и опубликованный head: `3920b9f1c45bb1174a21bfa8fdf64efb1f9bf16b`.
CI в тестовом repository отсутствует и не обозначен PASS. PR, source branch,
worktree и `evidence.json` сохранены; merge не выполнялся.

## Диагностика и лимиты Codex

Run различает `authentication`, `model_unavailable`, `rate_limit`, `protocol_error`
и `missing_artifact`; `publication unknown` остаётся отдельным состоянием без retry.
Карточка показывает модель, CLI version/session ID при наличии, время начала/конца,
duration, SHA, отчёт и страницы локальных логов. Usage относится только к этому
запросу и не является точным остатком подписки.

Подтверждённый rate limit (включая Title) сохраняет глобальную паузу в SQLite.
Уже работающие исполнители завершаются и освобождают слоты; новые ждут FIFO.
Структурированный `reset_at` (ISO/Unix seconds) или `retry_after` (seconds) задаёт
автоматическое продолжение. Без достоверного времени пользователь после восстановления
лимита нажимает «Лимит восстановлен — продолжить очередь». Пауза переживает restart,
но прерванные restart запуски автоматически не восстанавливаются.

«Повторить завершённый запуск» создаёт новую попытку с прежней моделью/config,
сохраняет старые ошибки/логи и repair budget, проверяет актуальность source перед CLI.
После аварии, неизвестной публикации или неуспешной проверки worktree повтор запрещён.
Ошибки CLI не переключают модель, API или billing и не расходуют repair budget.
Если агент вернул валидный результат, но последующая проверка или сохранение на backend
завершились ошибкой, на вкладке «Обзор» доступно «Продолжить по сохранённому результату».
Новая попытка использует `agent-result.json`, повторяет проверки source и переход этапа
без вызова модели. Это работает для Spec, Build, Review и Approve; публикация не повторяется.
Изменённый source, устаревшая Spec/Review и неустранённая ошибка по-прежнему блокируют переход.
Результаты старых запусков без `agent-result.json` автоматически из логов не восстанавливаются.
Во время выполнения карточка показывает время этапа, последнюю активность CLI и счётчики
фрагментов/символов streaming-ответа. Счётчики сохраняются не чаще раза в секунду и при
закрытии процесса, включая события `run/progress` в логе. Сырой текст deltas не сохраняется:
credentials могут пересекать границы фрагментов. Завершённые сообщения проходят redaction.
После 10 минут UI предупреждает о длительном этапе, даже если поток продолжает идти.
«Прервать этап» отправляет `turn/interrupt`; через 5 секунд без завершения backend посылает
SIGTERM группе процесса, затем SIGKILL через 3 секунды. Задача и worktree сохраняются.
Прерванный этап не получает PASS/READY; повтор доступен только после подтверждённого
завершения известных процессов и сверки source. Публикацию эта кнопка не прерывает.
Известные environment credentials и token/password signatures удаляются перед записью
новых артефактов/логов; конфигурация провайдера не читается и не журналируется.
Существующие артефакты не переписываются. Браузер читает только логи с отметкой
`log-format.json` / `redacted-v1`, которую новый executor сохраняет перед записью
санитизированного потока. Старые логи без этой отметки доступны только локально. Redaction не заменяет безопасную работу
самого full-access Codex с файлами пользователя.

## Инструменты рабочих агентов

Рабочие роли SW Factory наследуют настроенные в Codex MCP, computer/browser tools,
apps, plugins и hooks без дополнительных запретов со стороны приложения.
Запуски используют full access без sandbox и запросов approval. Агенты могут
самостоятельно проверять интерфейс доступными инструментами, включая управление
браузером и компьютером. Доступность инструментов зависит от конфигурации Codex
и разрешений ОС; глобальную конфигурацию приложение не меняет.

Генерация короткого заголовка (Title) остаётся изолированной: временный каталог,
без пользовательского config, tools и GUI. Интерактивные запросы разрешений от
MCP/tools через панель пока не поддерживаются.

Изменение применяется к новым запускам после перезапуска обновлённого backend.
Уже работающие процессы и задачи в `needs-human` автоматически не возобновляются.
Дождитесь завершения текущего исполнения перед restart, чтобы не прервать его.

Существующие относительные symlink на обычные файлы внутри worktree допускаются
при проверке source (например, `CLAUDE.md → AGENTS.md`). Хеш учитывает цель и её
содержимое. Внешние, битые ссылки, ссылки в `.git`, а также добавление или изменение
symlink в Build по-прежнему блокируются; ошибка указывает проблемный путь.
